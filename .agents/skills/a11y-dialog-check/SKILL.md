# 대화상자 접근성 검증

이 저장소는 대화상자를 라이브러리 없이 직접 만든다. Radix 같은 라이브러리가 대신하던 일을 구현이 빠뜨리지 않았는지 확인한다. 화면으로는 티가 나지 않는 자리다. 대화상자나 서랍을 만지는 작업은 종류를 가리지 않고 끝에 이 검증을 거친다.

## 기준

WCAG 2.2 AA를 쓴다. WCAG 3.0은 아직 완성되지 않았고 APCA는 확정 표준이 아니므로 판정에 쓰지 않는다.

**AAA 수치를 AA 기준으로 쓰지 않는다.** 터치 대상 44x44px은 AAA(2.5.5)다. AA(2.5.8)는 24x24px이고 예외가 넷 있다. 인라인(문장 속 링크), 간격(24px 지름 원이 다른 대상과 안 겹침), 동등(같은 일을 하는 큰 대상이 따로 있음), 필수(그 크기가 본질적임)다. 예외를 빼고 재면 통과할 것을 실패로 적게 된다.

## 네이티브 dialog가 대신하는 것

이 저장소의 Dialog는 네이티브 `dialog` 요소와 `showModal()`을 쓴다. 브라우저가 이미 하는 것을 다시 확인하거나 요구하지 않는다.

| 브라우저가 준다     | 그래서                                                                  |
| ------------------- | ----------------------------------------------------------------------- |
| 모달 의미와 역할    | `aria-modal` 속성이 DOM에 없어도 정상이다. 있는지 세지 않는다           |
| ESC 닫기            | 겹쳐 열 때 맨 위만 닫히는지만 본다                                      |
| 뒤 배경 비활성화    | top layer 밖은 포커스를 못 받는다. `aria-hidden`을 따로 요구하지 않는다 |
| 열릴 때 포커스 진입 | 어디로 들어가는지만 본다                                                |

Drawer는 Dialog에 데이터 속성만 얹은 래퍼다. Dialog에서 확인한 것을 Drawer에서 다시 확인하지 않는다.

## 우리가 확인하는 것

브라우저가 주지 않아 구현이 빠뜨릴 수 있는 것들이다. 눈으로 보면 대부분 통과처럼 보인다.

**1. 열릴 때 포커스가 안으로 들어가는가**

열고 나서 바로 Tab을 눌러 본다. 대화상자 안 요소로 가면 통과다. 페이지 맨 위 요소로 가면 실패다.

테스트로는 열린 직후 `document.activeElement`가 대화상자 안에 있는지 본다.

**2. Tab이 밖으로 새지 않는가**

안의 요소 개수보다 많이 Tab을 눌러 본다. 마지막 다음이 처음으로 돌아오면 통과다. 주소창이나 뒤 페이지로 가면 실패다.

Shift+Tab으로 반대 방향도 확인한다. 한쪽만 막힌 구현이 흔하다.

**3. 닫을 때 열었던 곳으로 돌아가는가**

열기 전에 어느 버튼에 포커스가 있었는지 기억하고, 닫은 뒤 Tab을 눌러 본다. 그 버튼 다음으로 가면 통과다. 페이지 처음부터 시작하면 실패다.

이걸 빠뜨리면 키보드 사용자는 닫을 때마다 위치를 잃는다.

**4. 이름이 붙었는가**

제목 요소가 `aria-labelledby`로 연결됐는지 본다. 역할과 모달 의미는 브라우저가 주지만 이름은 우리가 붙여야 한다. 이름 없는 대화상자는 스크린 리더에서 "dialog"라고만 읽힌다.

제목이 화면에 보이지 않는 대화상자면 `sr-only`로 넣는다.

**5. 겹쳐 열었을 때 맨 위만 닫히는가**

ESC 자체는 브라우저가 처리한다. 우리가 볼 것은 라이트박스 위에 무언가가 열린 상태에서 ESC를 눌렀을 때 맨 위 하나만 닫히는가다. 전역 리스너로 만들면 전부 닫힌다.

**6. 뒤가 스크롤되지 않는가**

열린 상태에서 마우스 휠을 굴리고 화살표를 눌러 본다. 뒤 페이지가 움직이면 실패다. 지금은 `html`에 붙는 `data-modal-open`과 `dialog.css`가 맡는다.

열 때 화면이 가로로 튀는지도 본다. 스크롤바가 사라지며 폭이 바뀌는 것을 보정하지 않으면 튄다.

## 추가로 보는 것

**바깥 클릭.** 대화상자 안에서 마우스를 누르고 밖에서 떼어 본다. 닫히면 실패다. 텍스트를 끌어 선택할 때 이 일이 생긴다.

**포커스 표시.** 안의 요소를 Tab으로 지나며 지금 어디에 있는지 보이는지 확인한다. 2px 두께에 배경 대비 3대 1 이상이어야 한다.

**터치 대상.** 닫기 버튼 같은 것이 24x24px 이상인지 본다(AA 2.5.8). 미달이면 위 기준 절의 예외 넷을 적용해 다시 판정한다. 아이콘이 작아도 클릭 영역은 커야 한다.

**모션 축소.** 시스템에서 모션 축소를 켜고 열어 본다. 위치를 옮기는 애니메이션이 죽는지 확인한다.

## 테스트로 만들기

눈으로 확인한 것은 다음 사람이 다시 확인해야 한다. 테스트로 남긴다.

확인하기 쉬운 것부터 쓴다. 포커스 위치와 속성 존재, 키보드 반응은 테스트가 쉽다. 스크린 리더 낭독은 어렵다.

```
열기 버튼을 누른 뒤 확인한다
  activeElement가 대화상자 안인가
  제목이 aria-labelledby로 이어졌는가
  html에 data-modal-open이 붙었는가

Tab을 요소 수보다 많이 누른 뒤 확인한다
  activeElement가 여전히 대화상자 안인가

ESC를 누른 뒤 확인한다
  닫혔는가
  activeElement가 열기 버튼인가
```

## 결과 내는 법

표로 낸다. 확인한 방법 칸을 비우지 않는다.

| 항목 | 판정 | 확인한 방법 | 실패면 무엇이 어긋났는지 |
| ---- | ---- | ----------- | ------------------------ |

**통과를 증명할 수 없으면 통과로 적지 않는다.** "구현했다"는 말은 근거가 아니다. 실행해서 확인하지 못한 항목은 "확인 못 함"으로 적고 무엇이 있으면 확인할 수 있는지 함께 적는다.

실패 항목에는 고칠 방향을 한 줄 붙이되 직접 고치지 않는다. 고치는 것은 만든 사람의 몫이다.

같은 항목이 세 번 실패하면 구현 방식 자체를 다시 보자고 보고한다. 네 번째 시도는 같은 이유로 실패한다.
