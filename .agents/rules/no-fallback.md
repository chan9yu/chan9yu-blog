# 오류를 감추지 않는다

## 규칙

**오류를 감싸 빈 값이나 기본값을 돌려주고 호출자에게 성공한 것처럼 보이게 하지 않는다.**

빈 배열과 빈 문자열, 0, 빈 객체는 정상 결과와 모양이 같다. 호출자는 실패를 알 수 없다. 화면은 그려지고 빌드는 통과하고 배포도 끝난다. 사고는 며칠 뒤에 "글이 검색에 안 잡힌다"는 모습으로 돌아온다.

## 이 규칙이 생긴 이유

v1.1.0으로 프로덕션에 처음 배포한 날 런타임에서 콘텐츠 파일을 읽다 실패하는 장애가 났다. v1.1.1은 그 읽기를 감싸 빈 값을 돌려주는 방식으로 장애를 덮었다. 페이지는 열렸지만 검색 색인이 조용히 비었다. v1.1.1은 회수됐다.

v1.1.2는 방향을 바꿨다. 런타임에 `contents/`를 읽는 코드 자체를 없애고 전부 빌드 타임으로 옮겼다. 읽기가 실패할 자리가 없어지니 감쌀 것도 없어졌다. 지금의 SSG 우선 원칙이 여기서 나왔다.

남은 교훈이 둘이다. 오류를 감싸지 않는다. 그리고 감싸고 싶어지는 자리는 대개 설계가 틀린 자리다.

## 금지하는 것

**실패를 정상 결과와 같은 모양으로 만드는 코드.**

```ts
export async function getAllPosts() {
	try {
		return await readPostsFromDisk();
	} catch {
		return [];
	}
}
```

글이 0개인 상태와 디스크를 못 읽은 상태가 같은 값이 된다. 목록 화면은 "아직 글이 없습니다"를 띄우고 검색 색인은 빈 채로 배포된다.

**비어 있는 catch.**

```ts
try {
	await revalidateTag("posts");
} catch {}
```

무엇이 실패했는지 아무 데도 남지 않는다.

**파싱 실패를 그럴듯한 기본값으로 메우기.**

```ts
const frontmatter = parseFrontmatter(raw) ?? { title: "제목 없음", tags: [] };
```

frontmatter가 깨진 글이 "제목 없음"으로 배포된다. 빌드가 멈췄어야 할 자리다.

**없는 값을 흘려보내기.** `data?.posts?.map(...) ?? []`처럼 물음표를 이어 붙이면 어느 단계가 비었는지 사라진다.

**재시도와 지연으로 미루기.** 의미 없는 `setTimeout`과 임시 플래그, 반복 재시도는 원인을 그대로 두고 증상이 나올 확률만 낮춘다.

## 대신 하는 것

**실패할 수 없는 설계로 바꾼다.** 가장 먼저 볼 선택지다. 값을 빌드 타임에 확정하고 값이 없으면 빌드를 멈춘다. `scripts/validate-seo.mjs`가 이 형태다. frontmatter가 규격에 맞지 않으면 배포가 나가지 않는다.

**던진다.** 서버 컴포넌트에서 던지면 `error.tsx`가 받는다. 빌드 타임에 던지면 배포가 멈춘다. 틀린 페이지가 프로덕션에 나가는 것보다 배포가 멈추는 편이 낫다.

**실패를 값의 타입에 남긴다.** 실패를 값으로 돌려줘야 하면 세 가지를 지킨다. 이름에 적고, 로그를 남기고, 호출자가 분기하게 한다.

```ts
export async function fetchPostViewsOrNull(slug: string) {
	try {
		const res = await fetch(`/api/views?slug=${encodeURIComponent(slug)}`, { cache: "no-store" });
		if (!res.ok) {
			console.warn(`[views] GET ${slug} failed: ${res.status}`);
			return null;
		}
		return (await res.json()).views;
	} catch (error) {
		console.warn(`[views] GET ${slug} network error`, error);
		return null;
	}
}
```

`null`이 반환값에 있으니 호출자는 분기해야 한다. 로그가 있으니 무슨 일이 있었는지 남는다.

## 허용되는 축소 동작

기능을 줄여서 계속 동작하게 만드는 것은 감추기와 다르다. 세 조건을 전부 만족할 때만 그렇다.

| 조건                            | 조회수 기능에서의 모습                        |
| ------------------------------- | --------------------------------------------- |
| 제품 결정이고 문서에 적혀 있다  | RUNBOOK의 "조회수가 안 보일 때"               |
| 실패한 상태가 화면에서 구분된다 | 숫자 대신 대시가 뜨고 인기 글이 최신순이 된다 |
| 실패가 로그에 남는다            | `console.warn("[views] ...")`                 |

로그가 빠지면 감춘 것이다. 화면 구분이 빠지면 틀린 값을 사실처럼 보여주는 것이다.

**흡수한 실패가 아래 단계에서 다시 뭉개지는 자리를 조심한다.** `fetchPostViewsOrNull`이 `null`을 제대로 돌려줘도 그 위에서 `?? 0`으로 받으면 "조회수 0"과 "조회수 모름"이 같아진다. RUNBOOK이 약속한 대시를 띄울 수 없다. `null`은 화면까지 살아가야 한다.

## 리뷰에서 볼 것

- `catch` 블록이 값을 돌려주면 그 값이 정상 결과와 구분되는가
- 비어 있는 `catch`가 없는가
- `?? []`와 `?? 0`, `?? ""`가 실패를 삼키고 있지 않은가
- 런타임에 `contents/`를 읽는 코드가 새로 들어오지 않았는가
- 새로 감싸려는 호출을 빌드 타임으로 옮길 수 있는가. 옮길 수 있으면 감싸지 말고 옮긴다
