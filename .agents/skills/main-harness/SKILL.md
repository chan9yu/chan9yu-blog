# 메인 하네스

이 저장소에서 코드를 만들거나 고치는 작업의 진입점이다. 무엇을 만들지는 요청이 정하고, 어떻게 굴릴지는 이 문서가 정한다.

## 먼저 범위를 판정한다

전부 팀으로 돌리면 한 줄 고치는 데 에이전트 넷이 붙는다. 아래로 가른다.

| 판정          | 조건                                                             | 어떻게                                         |
| ------------- | ---------------------------------------------------------------- | ---------------------------------------------- |
| 직접 한다     | 파일 하나에서 끝나고 새 파일이 없고 UI 표면이 안 바뀐다          | 고치고 게이트만 돈다                           |
| 일부만 부른다 | 한 영역에만 걸린다                                               | 해당 에이전트 하나에 맡기고 판정만 따로 받는다 |
| 팀으로 간다   | 새 파일이 생기거나 레이어가 여럿 걸리거나 대화상자 계열을 만진다 | 아래 흐름 전체                                 |

애매하면 좁게 잡는다. 하다가 넓어지면 그때 올린다.

## 누가 무엇을 하는가

에이전트 정의는 `.claude/agents/`에 있다. Agent 도구로 부를 때 `model: "opus"`를 명시한다.

| 에이전트        | 맡는 것                                       | 맡지 않는 것           |
| --------------- | --------------------------------------------- | ---------------------- |
| `fsd-architect` | 어느 레이어 어느 슬라이스에 둘지, import 방향 | 구현, 판정             |
| `ui-builder`    | 토큰 위에 컴포넌트 구현                       | 배치 결정, 합격 판정   |
| `a11y-verifier` | 접근성 판정                                   | 코드 수정              |
| `code-reviewer` | 저장소 규칙 위반 판정                         | 접근성 판정, 배치 결정 |

**만든 사람이 판정하지 않는다.** 이 분리가 하네스의 전부다. 구현자가 스스로 합격을 매기면 판정 단계는 없는 것과 같다.

## 흐름

```
배치 결정 (fsd-architect)
    아래로
구현 (ui-builder)
    아래로
판정 (a11y-verifier + code-reviewer, 병렬)
    아래로
게이트
```

배치가 자명하면 첫 단계를 건너뛴다. UI 표면을 안 건드리면 a11y-verifier를 건너뛴다. 건너뛴 단계는 왜 건너뛰었는지 한 줄 남긴다.

판정에서 실패가 나오면 구현으로 돌아간다. 같은 항목이 세 번 실패하면 구현 방식 자체를 다시 보자고 사용자에게 보고한다. 네 번째 시도는 같은 이유로 실패한다.

## 게이트

빠른 실패 먼저다. 앞이 깨지면 뒤를 돌리지 않는다.

```bash
pnpm type:check    # 가장 싸다
pnpm test
VERCEL_ENV=production pnpm build:strict   # frontmatter SEO 게이트 포함
pnpm lint
pnpm lint:arch     # Steiger
```

UI 표면을 건드렸으면 `pnpm test:e2e`를 더한다.

**게이트를 통과시키려고 테스트를 skip하거나 lint 규칙을 끄거나 단언을 느슨하게 고치지 않는다.** 그것은 통과가 아니라 게이트를 치운 것이다.

하나라도 실패하면 커밋하지 않는다. 증거 없이 통과했다고 적지 않는다.

## 이 저장소에서 실제로 깨지는 자리

일반적인 실수가 아니라 여기서 사고를 냈던 것들이다.

**route segment config를 재노출하면 라우트가 500이 난다.** `dynamicParams` 같은 것은 `app/`의 라우트 파일에 직접 적는다. metadata와 반대다.

**루트 `pages/`를 지우면 빌드가 E801로 멈춘다.** `src/pages`가 Pages Router로 잡힌다. 이 폴더에 라우트 파일을 만들어서도 안 된다.

**서버 전용 수출을 `index.ts`에 섞으면 빌드가 깨진다.** `node:fs`를 쓰는 것은 `index.server.ts`에만 둔다.

**런타임에 `contents/`를 읽으면 프로덕션에서 터진다.** 빌드 타임에 확정한다.

**오류를 감싸 빈 값을 돌려주면 조용히 배포된다.** 화면은 그려지고 검색 색인만 빈다. 실패는 값의 타입에 남기고 로그를 남긴다.

**`X-[value]` 임의값은 어긋남을 브라켓 안에 숨긴다.** 토큰이나 `@utility`로 옮긴다.

**주석의 기본은 0이다.** 외부 제약, 호출 순서 가정, 우회 코드의 근거, 회귀를 막는 이유 넷만 남는다. 일괄 삭제 전에는 `eslint-disable`과 `@vitest-environment` 같은 지시문을 먼저 전수 조사한다.

## 이어서 하는 작업

같은 대상을 다시 만질 때는 이전 산출물을 먼저 읽는다.

- 판정 기록이 있으면 지난 실패가 이번에 통과했는지 먼저 확인한다
- 사용자 피드백이 있으면 그 부분만 고친다. 전체를 다시 만들지 않는다
- 결정을 뒤집으면 이유를 밝힌다. 이유 없이 바꾸면 구현자가 어느 쪽을 따를지 알 수 없다

## 끝내는 법

**커밋과 푸시, PR 생성, 브랜치 생성은 사용자가 그때 명시적으로 요청할 때만 한다.** 지난번 승인이 이번 작업까지 이어지지 않는다.

**`contents/`는 별도 저장소다.** 글 본문을 승인 없이 고치지 않는다. 렌더링 문제는 렌더링 쪽에서 푼다.

**승인이 필요한 것.** 의존성 추가와 삭제, 아키텍처 변경, 빌드와 CI 설정 변경, 공개 타입 변경, 규칙 파일 수정.

## 참고

프리미티브 구현 절차는 `primitive-build`, 대화상자 접근성 검증은 `a11y-dialog-check` 스킬에 있다. 레이어 구조와 늘 지킬 것은 `AGENTS.md`, 룰 본문은 `.agents/rules/`에 있다.
