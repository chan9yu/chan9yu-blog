## 1. 크로스 임포트 해소 전략

크로스 임포트(같은 레이어 안 슬라이스 간 import, 예를 들어 `features/cart`에서 `features/product`로)는 스타일 문제가 아니라 구조적 경고 신호다.

1. 책임과 관리 주체가 모호해져 숨은 의존이 런타임 오류와 리뷰 비용을 낳는다
2. 슬라이스를 독립적으로 개발하고 테스트할 수 없게 된다
3. 코드 탐색 비용이 커진다
4. 단방향이 시간이 지나며 양방향 순환 의존으로 굳는다

공식 문서의 현행 규정은 절대 금지가 아니라 code smell이다. 일반적으로 피하는 편이 낫지만 의도적으로 쓸 수 있다. 도입한다면 신중한 아키텍처 결정으로 다뤄 근거를 문서화하고 주기적으로 재검토한다.

### entities 레이어에서

경계를 지나치게 잘게 나눴는지 먼저 본다. 슬라이스 병합이 자연스러우면 병합하고, 불가피할 때만 `@x`를 쓴다. 공식 문서 스스로 entities 크로스 임포트의 흔한 원인을 과잉 분할로 진단한다.

### features와 widgets 레이어의 4가지 전략

| 전략                          | 적용 시점                                                  | 방법                                                                                                                                             |
| ----------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A. 슬라이스 병합**          | 두 슬라이스가 항상 함께 바뀔 때                            | `features/profile`과 `features/profile-settings`를 하나로 합친다                                                                                 |
| **B. entities로 하향**        | 여러 feature가 같은 도메인 로직(세션 검증 등)을 반복 쓸 때 | `entities/session`을 만들어 도메인 타입과 로직만 내리고 UI는 features에 남긴다                                                                   |
| **C. 상위 레이어 조립**       | UI 조합이 필요할 때                                        | pages나 app에서 조합한다. render props, slot, props 주입. `CommentList`가 `UserAvatar`를 직접 import하지 않고 `renderUserAvatar` prop으로 받는다 |
| **D. Public API 제한 재사용** | 크로스 임포트가 정말 불가피할 때                           | 공개 public API만 쓴다. 내부 파일 직접 접근은 금지 유지                                                                                          |

A부터 C는 크로스 임포트 제거를 노리고, D만 크로스 임포트를 허용하되 경계를 엄격히 지킨다.

### 문제로 봐야 하는 신호

- 다른 슬라이스의 store, model, 비즈니스 로직에 직접 의존
- 내부 파일 deep import
- 양방향 의존(A가 B를, B가 A를 import)
- 한 슬라이스의 변경이 다른 슬라이스를 자주 깨뜨림

## 2. Desegmentation (기술 역할별 묶기)

코드를 비즈니스 도메인이 아니라 기술 역할로 묶는 구성이다. `components/`, `utils/`, `stores/`에 여러 도메인 코드가 섞인다. FSD를 쓴다는 코드베이스 안에서도 발생한다(`features/delivery/ui/components`, `entities/recommendations/utils`).

- 파일 단위에서도 생긴다. 하나의 `types.ts`나 `utils.ts`에 delivery 도메인과 user 도메인이 함께 있으면 같은 문제다.
- 결과: 한 기능을 고치는 데 여러 폴더를 오가고(낮은 응집), 결합이 높아지고, 리팩터링이 어려워진다.
- 해결: 도메인별로 묶고 무엇을 다루는지 드러나는 이름을 쓴다. `types.ts`를 `delivery.ts`와 `user.ts`로 나눈다.

## 3. 과잉 entities와 과잉 슬라이스

entities는 낮은 레이어라 접근성이 높고, 수정하면 상위 여러 슬라이스에 파급된다. 남발하면 경계가 모호해지고 결합이 올라간다.

판단 기준 여섯.

1. entities 레이어가 없어도 FSD 위반이 아니다. thin client 앱이면 불필요할 수 있다
2. 처음에는 페이지나 위젯의 `model`에 두고 재사용이 확인됐을 때만 entities로 옮긴다
3. 모든 비즈니스 로직이 entity를 필요로 하지 않는다. 백엔드 응답 타입은 `shared/api`에, 재사용 로직만 entity `model`에 둔다
4. 단순 CRUD는 `shared/api`로 충분하다. 여러 요청의 일관성과 트랜잭션 처리가 필요할 때만 entities를 검토한다
5. 인증 데이터(토큰, 로그인 응답의 사용자 정보)는 `shared/auth`나 `shared/api`에 둔다. 인증 맥락에 종속적이라 재사용성이 낮다
6. `@x`를 최소화한다. order, order-item, order-customer-info를 쪼개 상호 import하는 대신 `order-info` 하나로 합친다

과잉 슬라이스는 도구가 잡는다. Steiger의 `insignificant-slice`는 한 페이지에서만 쓰이는 entity나 feature를 그 페이지로 합치라고 제안하고, `excessive-slicing`은 한 레이어의 슬라이스가 지나치게 많으면 경고한다.

shared 비대화도 같은 계열의 문제다. 재사용 가능하다는 이유만으로 shared에 두지 않는다. 실제로 여러 곳에서 쓰일 때 내린다. `shared/types` 폴더는 금지다.

## 4. 배럴 파일과 Next.js 성능

FSD의 public API 규칙은 배럴 파일(index.ts)로 구현되는데, 배럴은 Next.js에서 실제 비용을 치른다. 공식 FSD 문서도 이 문제를 인정한다. 규칙을 버리는 것이 아니라 배럴을 잘게 유지하는 것이 답이다.

### 무엇이 얼마나 느려지나

- 개발 서버는 tree-shaking을 하지 않는다. 배럴에서 하나만 import해도 배럴이 끌어오는 모듈 전부가 컴파일된다. 훅 하나를 배럴로 import했더니 배럴에 묶인 훅 120여 개가 전부 컴파일되어 552kB 청크가 만들어지고, 직접 import로 바꾸자 64kB로 줄어든 사례가 보고돼 있다.
- Vercel의 측정으로는 배럴을 가진 인기 패키지의 import 자체에 개발 모드에서 200~800ms가 걸린다.
- 배럴은 import 순환이 코드베이스에 들어오는 가장 흔한 경로다.

### optimizePackageImports는 로컬 배럴을 돕지 않는다

Next.js의 `optimizePackageImports` 설정은 npm 패키지의 배럴 import를 컴파일러가 직접 import로 바꿔 주지만, 대상이 패키지다. `src/` 안의 FSD 배럴에는 적용되지 않는다. 모노레포에서 심링크된 워크스페이스 패키지의 배럴에 Turbopack이 이 최적화를 적용하지 못하는 문제도 열려 있다(Next.js 이슈 75148, 16.2에서도 재현 보고). 로컬 배럴의 비용은 구조로 줄이는 수밖에 없다.

### 서버와 클라이언트 혼합 배럴

서버 컴포넌트와 클라이언트 컴포넌트를 한 배럴로 함께 내보내면 서버 컴포넌트가 클라이언트 컴포넌트로 표시되는 문제가 보고돼 있다(Next.js 이슈 63441). 서버 전용 수출이 섞이면 빌드 오류로 번진다. 해법은 `index.server.ts` 분리다. `nextjs-integration.md`의 public API 분리 절에 있다.

### 완화 규칙 정리

1. `shared/ui`와 `shared/lib`은 거대 배럴 하나 대신 컴포넌트와 라이브러리 단위 index를 둔다. `@/shared/ui`가 아니라 `@/shared/ui/button`으로 import한다
2. 슬라이스 index에서 wildcard(`export *`)를 쓰지 않고 필요한 것만 선별한다. 배럴이 작을수록 비용도 작다
3. 슬라이스 index가 있으면 `ui/index.ts` 같은 중첩 index를 만들지 않는다
4. 같은 슬라이스 내부는 상대 경로로 import해서 자기 배럴을 거치지 않는다. 순환을 막는다
5. 서버 전용 수출은 `index.server.ts`로 분리한다
6. IDE 자동완성이 내부 경로를 추천해 public API를 우회하는 일은 도구로 막는다(`tooling.md`)

## 5. FSD가 맞지 않는 경우

도입을 결정하기 전에 확인한다. 커뮤니티 도입 후기에서 반복해서 나오는 지점들이다.

- **소규모 프로젝트에는 과하다.** 화면 몇 개짜리 앱에 6레이어를 깔면 구조 자체가 비용이 된다. 필요한 레이어만 쓰는 것이 FSD의 공식 입장이기도 하다. shared, pages, app으로 시작해서 필요할 때 늘린다.
- **학습 곡선이 가파르다.** 슬라이스 이름 짓기, lib과 model 중 어디에 둘지 같은 판단이 초기에 팀 생산성을 떨어뜨린다는 후기가 흔하다. 판단 기준을 팀 문서로 정리하고 `SKILL.md`의 판단 기준 표 같은 대응표를 공유하면 갈등이 줄어든다.
- **자동 강제 없이는 유지되지 않는다.** 린터 없이 규칙 문서만으로 도입하면 개발자마다 해석이 갈려 몇 달 안에 무너진다. 도입 첫날부터 Steiger를 건다.
- **오래된 자료가 많다.** 2024년 이전 글은 폐기된 processes 레이어를 현행처럼 소개하고, widgets를 재사용 UI 컴포넌트 자리로 잘못 설명하는 글도 있다. 발행일을 확인하고 fsd.how의 현행 문서와 대조한다. feature-sliced.design 도메인은 스팸이 주입된 옛 사본이므로 출처로 삼지 않는다.
- **파일 라우팅 프레임워크와의 마찰은 상수다.** Next.js의 라우팅 규약과 FSD 레이어는 영원히 겹친다. `nextjs-integration.md`의 개명 패턴이 마찰을 줄이지만 없애지는 못한다. 팀이 이 비용을 받아들일지 먼저 정한다.
