# v1.3.0 재작성 오케스트레이터

기존 코드를 옮기는 것이 아니라 처음부터 다시 만든다. 기능은 v1.2.0과 같아야 한다. 그것이 이 릴리스의 판정 기준이다.

**실행 모드:** 에이전트 팀

## Phase 0: 컨텍스트 확인

시작하기 전에 지금이 어떤 실행인지 정한다.

| 상황                                | 모드        | 할 일                                            |
| ----------------------------------- | ----------- | ------------------------------------------------ |
| `_workspace/`가 없다                | 초기 실행   | Phase 1부터 전부                                 |
| `_workspace/`가 있고 부분 수정 요청 | 부분 재실행 | 해당 에이전트만 다시 부른다                      |
| `_workspace/`가 있고 새 대상 요청   | 새 실행     | `_workspace/`를 `_workspace_prev/`로 옮기고 시작 |

부분 재실행일 때는 이전 산출물을 먼저 읽는다. 에이전트에게도 이전 결과를 읽고 이어 하라고 알린다.

## Phase 1: 범위 확정

무엇을 만들지 정한다. 정본은 셋이다.

- 기능이 어떻게 동작해야 하는가: `docs/product/SPEC.md`
- 화면이 어떻게 놓여야 하는가: `docs/design/DESIGN-SPEC.md`
- 어떤 값을 쓰는가: `docs/design/DESIGN.md`

기존 `src/` 코드는 참조 자료로만 본다. 옮겨 쓰지 않는다.

이번에 만들 대상 목록을 `_workspace/01_scope.md`에 적는다. 목록이 브랜치 하나에서 끝나는 크기를 넘으면 쪼갠다.

## Phase 2: 배치 결정

fsd-architect를 부른다. 만들 대상이 어느 레이어와 슬라이스, 세그먼트에 갈지 정한다.

구현 전에 배치가 서야 한다. 만들고 나서 옮기면 import를 두 번 고친다.

산출물은 `_workspace/02_layout.md`다. 표로 내고 근거 칸을 비우지 않는다.

## Phase 3: 구현

팀을 만들고 작업을 나눈다.

```
TeamCreate(members: [fsd-architect, ui-builder, a11y-verifier, code-reviewer])
```

ui-builder가 만든다. 배치가 애매하면 fsd-architect에게 직접 묻는다. 대화상자 계열을 만들면 a11y-verifier에게 검증을 요청한다.

토큰이 먼저다. 컴포넌트가 쓸 값이 서 있어야 컴포넌트를 만든다. 토큰과 컴포넌트를 같이 만들면 값이 컴포넌트마다 갈라진다.

산출물은 실제 코드와 `_workspace/03_build_notes.md`다. 노트에는 새로 만든 토큰과 대화상자 일곱 항목 처리 방식을 적는다.

## Phase 4: 검증

세 갈래로 동시에 본다.

**a11y-verifier**는 대화상자 일곱 항목과 키보드, 대비, 터치 대상을 본다. 산출물은 `_workspace/04_a11y.md`다.

**code-reviewer**는 오류를 감추는 코드와 런타임 콘텐츠 의존, 임시 우회, 주석 총량을 본다. 산출물은 `_workspace/04_review.md`다.

**fsd-architect**는 import 방향과 슬라이스 간 참조를 본다. 산출물은 `_workspace/04_boundary.md`다.

셋 다 판정만 하고 고치지 않는다. 고치는 것은 ui-builder다.

## Phase 5: 반영과 재검증

지적을 ui-builder에게 넘겨 고친다. 고친 뒤 해당 검증자에게 다시 보낸다.

**세 번 돌고도 같은 항목이 실패하면 멈춘다.** 네 번째 시도는 같은 이유로 실패한다. 구현 방식이나 명세 해석이 잘못됐다는 뜻이므로 사용자에게 보고한다.

## Phase 6: 게이트

전부 통과해야 끝이다. 순서는 빠른 것부터다.

```bash
pnpm type:check
pnpm test
pnpm build:strict
pnpm lint
```

통과시키려고 테스트를 건너뛰거나 규칙을 끄지 않는다. 그것은 통과가 아니라 검사를 치운 것이다.

## Phase 7: 기록과 피드백

`docs/product/ROADMAP.md`의 v1.3.0 계획에서 끝난 항목에 체크한다.

사용자에게 묻는다. 결과에서 고칠 것이 있는지, 팀 구성이나 순서에서 바꾸고 싶은 것이 있는지. 답이 없으면 넘어간다.

피드백이 오면 어디를 고칠지는 유형에 따라 다르다.

| 피드백           | 고칠 곳           |
| ---------------- | ----------------- |
| 결과물 품질      | 해당 스킬         |
| 에이전트 역할    | 에이전트 정의     |
| 순서             | 이 오케스트레이터 |
| 트리거가 안 걸림 | 스킬 description  |

같은 유형의 피드백이 두 번 오면 하네스를 고치자고 먼저 제안한다.

## 데이터 전달

**메시지.** 팀원 간 질문과 지적은 SendMessage로 직접 주고받는다.

**태스크.** 진행 상황과 의존 관계는 TaskCreate로 공유한다.

**파일.** 산출물은 `_workspace/`에 남긴다. 이름은 `{순번}_{이름}.md`다. 중간 파일을 지우지 않는다. 나중에 왜 그렇게 정했는지 되짚을 때 쓴다.

## 에러 처리

**에이전트가 실패하면** 한 번 다시 부른다. 또 실패하면 그 결과 없이 진행하고 무엇이 빠졌는지 보고서에 적는다. 빠진 것을 채운 척하지 않는다.

**판정이 갈리면** 삭제하지 않고 양쪽을 출처와 함께 남긴다. 사용자가 고른다.

**정보가 부족하면** 멈추고 무엇이 필요한지 적는다. 그럴듯한 기본값을 채우지 않는다. 임시로 정한 값은 그대로 굳는다.

## 승인이 필요한 것

다음은 진행하지 말고 사용자에게 묻는다.

의존성 추가와 삭제, 빌드 설정 변경, 공개 타입 변경, 규칙 파일 수정, `contents/` 서브모듈 수정, git 쓰기 작업 전부.

## 테스트 시나리오

**정상 흐름.** "Dialog 직접 만들어줘"라고 요청한다. Phase 0에서 초기 실행으로 판정하고, Phase 2에서 fsd-architect가 `shared/ui`로 배치를 정하고, Phase 3에서 ui-builder가 만들고, Phase 4에서 a11y-verifier가 일곱 항목을 검증하고, 실패 항목을 고쳐 재검증한 뒤, Phase 6 게이트를 통과한다.

**에러 흐름.** a11y-verifier가 "닫을 때 포커스 복원" 실패를 세 번 연속 판정한다. Phase 5의 규칙에 따라 네 번째를 시도하지 않고 멈춘다. 구현 방식을 다시 보자고 사용자에게 보고한다.
